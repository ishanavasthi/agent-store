# Merchant identity is a token presented in-protocol on a separate MCP face, and extraction never happens client-side

A Merchant adding products from chat connects to `/merchant/mcp` — a second, tool-disjoint MCP face beside the buyer's `/mcp` — and identifies itself by passing `merchantToken` (`mrc_tok_…`) as an ordinary argument on every tool call, exactly as a buyer passes `agentToken`. The transport stays authless on both faces (PLAN §3, §5.2). A token matching no Merchant answers `UNKNOWN_MERCHANT_TOKEN` in the Refusal shape, recoverable, with no audit event written.

The face's front door is `submit_catalog_item`, and what crosses the chat→server gap is deliberately the *smallest* thing that can: the caption **verbatim** as the merchant wrote it, plus at most one photo (a public `imageUrl` the server fetches, or inline base64). Never an extracted field. The server then runs that caption through the same Ingestion pipeline `npm run ingest:demo` runs — Extraction model, assembly rules, confidence gate — so a chat submission and a dataset ingest reach `published` or Held by identical rules. A field the caption never stated (almost always stock) holds the whole Product and costs one more chat turn through `confirm_product`; it does not cost a trip to the web confirmation screen.

## Why

**Why in-protocol rather than a transport header.** The buyer face already made this choice and the reasons carry over unchanged: a claude.ai custom connector configured with no authentication cannot attach a header, identity that lives in the protocol is visible in the audit trail and in the tool schema a model reads, and one habit across both faces means one thing to explain. A `merchantToken` argument is also the only shape that works when the same deployment must be reachable by a connector, by `curl`, and by the test client, with no per-transport variation.

**Why a separate face rather than authorization inside shared tools.** Tool-set isolation is a stronger boundary than a runtime check, and it is a boundary the *model* can see: a buyer agent connected to `/mcp` is never shown a tool that edits a catalog, so there is no prompt that can talk it into calling one. One face with `if (isMerchant)` branches inside shared handlers would put catalog-editing tools in every buyer's tool list and make every future tool a permission question. Two mounts of the same stateless helper cost one line each.

**Why extraction never runs client-side.** The confidence gate is the product. If a connector could send `{name, price, stock}` it would be reporting a model's reading of a caption *without* the confidence numbers the gate is made of, and every submission would arrive at 1.0 confidence by construction — the gate would publish everything, the demo beat would vanish, and stock would be a number some client guessed rather than one the merchant stated. Keeping extraction server-side also keeps the accuracy record honest: the numbers in `fixtures/demo-dataset/runs/` describe the code path that actually runs in production, because there is only one. The MCP SDK has no image-typed tool argument, so a connector could not forward attachment bytes even if we wanted it to; the caption (or the verbatim visible text of a screenshot) is what the client can honestly supply.

## Consequences

- **The token appears in chat transcripts.** The merchant types or pastes `mrc_tok_…` into a claude.ai conversation, and the model repeats it on every tool call, so it is stored wherever that conversation is stored. Accepted for v1 (decision D4, 2026-09-03): one merchant, one store, test-mode payment rails, and no tool on the face can delete anything — the worst a leaked token buys is a mis-submitted Product, which `npm run catalog:archive` puts back to `draft`.
- **Rotation is an operator action, not a tool.** There is no rotate-token tool and no admin endpoint. Rotating means setting `MERCHANT_TOKEN` to a new value in the deployment's environment and redeploying — and, because a token already minted on the row is never rotated by the seed, rotating a *live* store means clearing `merchants.token` for that row first. This is the deliberate v1 shape: token custody is deployment configuration, and a self-service rotation tool would be a second way to lock yourself out of your own catalog.
- **Adding a merchant tool means touching one file** (`src/mcp/merchantServer.ts`) and no buyer code; the buyer's tool list cannot grow by accident. `src/http/mcpFaces.integration.test.ts` pins both tool sets, so a tool that leaks across faces fails a test rather than shipping.
- **`/merchant/mcp` must be mounted before the `/merchant` confirmation router**, or that router answers the MCP path and the connector never handshakes. Route order is now load-bearing and is commented as such in `src/http/app.ts`.
- **A deployment with no extraction key still boots and sells.** Extraction is optional at the composition root: `submit_catalog_item` alone answers `EXTRACTION_NOT_CONFIGURED`, and the catalog, the buyer face and the money path are untouched. The reverse — making an LLM key a boot requirement — would let an expired key take the storefront down.
- **The merchant face writes no audit event for an identity failure.** The audit log is the money ledger (ADR-0003), and a mistyped merchant token is not a money event. `UNKNOWN_MERCHANT_TOKEN` is therefore a Refusal *shape* the rule-auditor never sees, which is stated in CONTEXT.md → Refusal so the borrow cannot be mistaken for a fourth failure kind.
